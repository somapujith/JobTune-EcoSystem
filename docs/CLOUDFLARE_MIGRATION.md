Read [migration/CUTOVER.md](migration/CUTOVER.md) for the evidence, the defects the live run found, and the known limitations. The text below is the original porting plan and the detailed history.

Status: **the Express backend is fully ported to Hono in the working tree (see "Implementation status" below), but NOT deployed, NOT cut over, and the Phase 0 gate is not fully met (S11 passed locally against Postgres through Neon's WebSocket proxy, but has not been run on a hosted Neon branch).** The `backend/` project is connected to Cloudflare Workers via **Cloudflare's native Git integration** (Workers & Pages → project → Settings → Build): it deploys automatically on push using `backend/wrangler.toml`. **Heads-up:** once the ported `src/worker-entry.js` is pushed to the connected branch, that deploy serves the full API on `jobtune-ecosystem.somapujith.workers.dev` (with no secrets set it fails closed: 500s / degraded health). Production traffic is unaffected until `frontend/vercel.json` is changed, which this work has not done. This doc was the original porting plan (written 2026-09-14); the decision record is [migration/ADR-001-cloudflare-workers-port.md](migration/ADR-001-cloudflare-workers-port.md).

## Deploy mechanism

- **Live path:** Cloudflare's Git integration, configured entirely in the Cloudflare dashboard (Build command: none, Deploy command: `npx wrangler deploy`, Root directory: `/backend`). No `CLOUDFLARE_API_TOKEN` or GitHub secret is involved in this path — Cloudflare's own GitHub App has repo access and builds/deploys directly.
- A GitHub Actions–based deploy (`wrangler-action` + a `CLOUDFLARE_API_TOKEN` repo secret) was scaffolded and then removed to avoid two competing deploy paths — Cloudflare's Git integration is the one actually in use. If a CI-gated deploy (tests/lint before deploy) is wanted later, re-add that workflow *and* disconnect the native Git integration first, rather than running both.
- `wrangler` is pinned as a `devDependency` in `backend/package.json` (`4.131.2`, matching what Cloudflare's build environment resolved) so local `npx wrangler` and CI use the same version.
- **Project identity matters and must match exactly:** the Cloudflare Workers project name (`jobtune-ecosystem`) and `account_id` (`af2854d5e1c39fde573717202a1deb36`) in `wrangler.toml` must match the actual connected Cloudflare project — an earlier attempt used a different, incorrect `account_id`/project name pair copied from a mismatched dashboard session, and the build failed hard with `The account_id in your wrangler.toml file must match the account_id for this account`. If a future deploy fails the same way, re-check both values against the Cloudflare dashboard's Workers & Pages overview for this exact project before assuming it's a code problem.
- Deployed URL: `jobtune-ecosystem.somapujith.workers.dev`.

## Why this isn't a drop-in deploy

Cloudflare Workers runs on V8 isolates, not Node.js. There's no filesystem, no raw TCP sockets, no native addons, and no long-running process — every request gets a `fetch(request, env, ctx)` handler instead of `app.listen()`. `nodejs_compat` (enabled in `wrangler.toml`) polyfills a good chunk of the Node API surface, but it does not make native addons or TCP-based DB drivers work.

Concretely, in this codebase today:

| Concern | Current implementation | Workers-compatible? |
|---|---|---|
| HTTP framework | Express 5 (`src/app.js`, `app.listen()`) | No — needs a Workers-native router (Hono recommended — Express-like API, built for Workers) or hand-rolled `fetch` routing |
| Database driver | `pg` ([config/database.js](../backend/src/config/database.js)) — raw TCP `Pool` | No — swap to [`@neondatabase/serverless`](https://github.com/neondatabase/serverless), which speaks HTTP/WebSocket. Since the DB is already Neon, this is a driver swap, not a DB migration |
| Password hashing | `bcrypt` (native addon) — used in [routes/auth.js](../backend/src/routes/auth.js), [services/sessionService.js](../backend/src/services/sessionService.js) | No — swap to `bcryptjs` (pure JS, same API) or rewrite on Workers' native `crypto.subtle` (PBKDF2/scrypt) |
| File uploads | `multer` — used in [routes/atsCheckerV2.js](../backend/src/routes/atsCheckerV2.js), [routes/resume.js](../backend/src/routes/resume.js), [routes/resumeV2.js](../backend/src/routes/resumeV2.js) | No — replace with the Web `Request.formData()` API, which Workers supports natively |
| PDF/DOCX generation & parsing | `pdfkit`, `docx`, `mammoth`, `jszip`, `unzipper`, `xml2js` — used across [routes/resume.js](../backend/src/routes/resume.js), [routes/resumeV2.js](../backend/src/routes/resumeV2.js), [services/resumeExport.js](../backend/src/services/resumeExport.js), [services/v2/resumeExportEngine.js](../backend/src/services/v2/resumeExportEngine.js), [utils/fileParser.js](../backend/src/utils/fileParser.js) | **Verified in the Phase 0 spike (see "Phase 0 spike results" below):** all work in workerd, but `pdf-parse`, `unzipper`, `pdfkit` and the `mammoth` call style each need a build alias/stub or a call-site change. No Containers carve-out is needed |
| SSR frontend serving | `fs.readFileSync` / dynamic `import()` of a built bundle — [ssr/setupFrontend.js](../backend/src/ssr/setupFrontend.js) | No — Workers has no filesystem. Needs Cloudflare's Assets binding (static files) and a different way to invoke the SSR render function (no dynamic `import()` from disk) |
| Admin static bundle | `express.static('public/admin')` — [app.js:94](../backend/src/app.js) | No — same fix as above, via Assets binding |
| JWT signing | `jsonwebtoken` | Likely fine under `nodejs_compat`, but worth confirming — Workers' native `crypto.subtle` is the lower-risk alternative if issues surface |
| Logging | `winston` (console transport only — no file transport found in this codebase) | Likely fine — no filesystem writes detected, just console output |
| Outbound HTTP | `axios` (Adzuna API, LM Studio, Anthropic SDK) | Fine — Workers supports `fetch` natively; `axios` itself should work under `nodejs_compat`, or these call sites could move to native `fetch` to drop the dependency |

## Porting plan (suggested order)

1. **✅ Done — DB driver.** [config/database.worker.js](../backend/src/config/database.worker.js) wraps `@neondatabase/serverless`'s `Pool` (API-compatible with `pg`'s `.query()`, so ported routes' query calls don't need to change) behind a `getPool(env)` function — Workers has no `process.env`, so the connection string comes from the `env` object passed into `fetch(request, env, ctx)` instead. Smoke-tested against the live Neon DB (`SELECT COUNT(*) FROM users` returned the correct count). **Kept as a separate file from [config/database.js](../backend/src/config/database.js) on purpose** — the live Express app still uses `pg`/`database.js` unchanged and untouched; route files should only import `database.worker.js` once they're actually being ported, module by module, not as a blanket swap.
2. **Pick and wire a Workers-native router.** Hono is the closest match to Express's `app.use('/api/x', router)` mounting style already used in [app.js](../backend/src/app.js) — minimizes the diff across all ~28 route files.
3. **Replace `bcrypt` with `bcryptjs`** in [routes/auth.js](../backend/src/routes/auth.js) and [services/sessionService.js](../backend/src/services/sessionService.js) — same API, drop-in.
4. **Rewrite file-upload handling** (3 route files) from `multer` middleware to `await request.formData()`.
5. **Test each document-processing dependency in isolation** under `nodejs_compat` (`pdfkit`, `docx`, `mammoth`, `jszip`, `unzipper`, `xml2js`) before porting the routes that use them — if any fail, the fallback is Cloudflare's Node.js-compatible container product (see "Alternative" below) for just that route, or re-implementing the specific operation.
6. **Move SSR + admin static serving to Cloudflare Assets.** This is the most involved piece — `setupFrontend.js`'s `fs`/dynamic-`import()` pattern needs a real rewrite, not a swap.
7. **Port route files module by module**, using the module docs in [docs/modules/](modules/) as the checklist of what each route actually does — verify plan-gating (`requirePlan`) and auth middleware behavior are preserved, since those are security-relevant.
8. **Move all secrets out of `.env` into `wrangler secret put`** — `JWT_SECRET`, `DATABASE_URL`, `ADZUNA_APP_KEY`, `LM_STUDIO_URL`, etc. Workers doesn't read `.env` files at runtime.
9. **End-to-end test every module** against the deployed Worker before cutting traffic over — pay particular attention to the known existing bugs listed in [docs/README.md](README.md#cross-module-findings-from-code-not-speculation), since porting is a good opportunity to fix them but a bad time to accidentally mask or change their behavior unintentionally.

**Required build config** (all three go in `backend/wrangler.toml` `[alias]`): stub `@aws-sdk/client-s3`; stub `node-ensure` (CJS, non-recursive); `pdfkit` → `pdfkit/js/pdfkit.standalone.js`. Stubs live in `backend/spike/docs/stubs/` and are proven by `wrangler.fixed.toml`.

**Bundle size** (`wrangler deploy --dry-run`; limits 3 MB gzip Free / 10 MB gzip Paid): doc-processing modules alone are 2.62 MiB gzip as-is, 1.38 MiB with the pdf.js pin — the as-is form leaves almost no Free-plan headroom for Hono/Neon/joi. Keep doc libs behind lazy `import()`.

**CPU / plan decision (not in the ADR):** bcryptjs at cost 10 measured ~70–80 ms wall per hash *and* per compare in workerd; document ops were 24–180 ms. The Workers **Free** plan's CPU cap is 10 ms/request (from memory — verify against current Cloudflare docs), so login, signup and document routes need the **Paid** plan. Do not lower the bcrypt cost to fit.

### Corrections to ADR-001 found by the spike

1. **§4.1 is overstated.** With compat date `2026-09-14` + `nodejs_compat`, `process.env` **is populated** with `[vars]`/secrets at module load and request time (`nodejs_compat_do_not_populate_process_env` or a pre-2025 compat date makes it empty), and `process.exit` **exists**. In-request `process.exit(1)` cancels the request with a 500 (isolate survives); at **module load it is a silent no-op**, so a missing `JWT_SECRET` does not fail loudly — the Worker serves with `undefined`. The `createConfig(env)` design is still right, but the reason is *fail loud in the request path*, not "the isolate dies". `NODE_ENV`, `PORT`, `FRONTEND_URL` must still be set as vars.
2. **pdf-parse 1.1.4 has no `module.parent`/`test/data` debug branch** (`index.js` is two lines). The real hazards are the dynamic-require glob and the `node-ensure` recursion above.
3. **unzipper fails at build time, not runtime** (unresolvable optional `@aws-sdk/client-s3`), and pdfkit fails on `__dirname` before it reaches any `fs`/`.afm` issue.
4. **The `requirePlan` call-site count is 90, not 100** (generated from the AST; see `docs/migration/manifest.render.md`). The ADR figure counted comment lines and the definition line; community is 12 (not 14) and aiCoach 7 (not 11). Tier split: 57 / 21 / 12 for tiers 1 / 2 / 3. All other measured numbers reproduce at git `HEAD` (41 files, 41 mounts, 181 route-file endpoints).
5. **Public (no `authenticateToken`) surface is exactly 7 endpoints:** `POST /api/auth/{signup,login,refresh,logout}`, `GET /api/subscriptions/plans`, `GET /api/learning/resources`, `GET /api/health`.
6. **Unrelated pre-existing issue to check on Render:** in plain Node, `pdfParse(Buffer)` intermittently failed with `bad XRef entry` when several different PDFs were parsed in one process (4/11 ok); `pdfParse(new Uint8Array(buf))` gave 11/11. Root cause not established; workerd did not trigger it. Worth checking whether production is already affected.
7. **Pre-existing behavior to preserve, not fix, during the port (ADR §4.3):** `fileParser`'s DOCX text includes xmlns URLs/attribute strings; `ResumeExport.toDOCX` drops unsectioned lines.

## Implementation status (2026-09-19)

Built in the working tree (uncommitted; Render/Express code untouched): `backend/src/worker/**` (Hono app, 41 route files / 184 endpoints, services as DI factories), `backend/src/worker-entry.js`, `backend/wrangler.toml` `[alias]` section, per-slice notes in `docs/migration/wave/*.md`, verification tooling in `backend/scripts/migration/`, and the runbook [migration/verification-runbook.md](migration/verification-runbook.md).

**Evidence produced locally (synthetic data, no production access):**
- `npx jest` (whole backend): 154 suites / 4,870 tests pass. These prove ported logic against fakes and byte-compare SQL/literals with the Express originals. **They do not prove SQL, Neon behavior, or runtime limits (ADR Phase 4 note).**
- `npm run migration:parity`: Worker manifest vs Render reference manifest — **184/184 endpoints, 0 differences** in auth coverage and `requirePlan` tier (ADR checklist 5, 6 in static form).
- `npm run migration:bundle`: built bundle has **0** references to `initializeTables|runMigrations|ensureTables` (checklist 19); 9.9 MiB raw / 1.87 MiB gzip (Free plan limit 3 MB gzip; the doc-processing libraries are the bulk).
- `npm run migration:smoke`: the real entry boots in local workerd, degrades cleanly with no DB, 401s without a token, masks 5xx errors, enforces CORS (checklist 21, 22, locally).
- Per-slice runs in local workerd for the highest-risk pieces (uploads/exports, auth/session flows).

**Not done / needs you (cannot be done from this repo alone):**
1. **Phase 0 gate S11, hosted-Neon step** — the driver, lifecycle and load behavior are proven locally (see the S11 row above and `docs/migration/s11-results.md`); what remains is running the same scripts against a Neon **branch** (section 10 of that file). Needs your Neon console; not the production branch.
2. **Real-data checks**: bcryptjs vs real production hashes (S7), Render-issued JWTs (S9), `CF-Connecting-IP` through the Vercel proxy (checklist 7 — predicted fail-open for single-device enforcement if Vercel's egress IP arrives instead of the user's).
3. **Plan/cost decision**: bcryptjs cost 10 (~70 ms CPU) and document ops exceed the Free plan's 10 ms CPU cap — login, signup and doc routes need the **Workers Paid plan**.
4. **Rate limiting is now provisioned in `wrangler.toml`** (`AUTH_LIMITER` 5 per 60 s **per account** on login/signup, keyed by email because production data shows every user arriving from ~2 shared proxy IPs; `API_LIMITER` 300 per 60 s per IP as a flood backstop). Workers rate-limit bindings only allow 10 s / 60 s windows, so the original 20-per-15-minutes is not reproduced exactly. **Configured, not yet observed throttling** (checklist 18): run `npm run migration:ratelimit` against a test account after the secrets are set.
5. **Secrets**: none are set yet. Rate limiting (item 4) is now in place, so it is safe to set them: `backend/scripts/migration/set-worker-secrets.ps1` (values via stdin, never on a command line; generates a NEW `JWT_SECRET`). Non-secret vars (`NODE_ENV`, `FRONTEND_URL`, `AI_PROVIDER`, `GEMINI_MODEL`, `MOCK_AI`) are in `wrangler.toml [vars]`. `LM_STUDIO_URL` is intentionally unset (its Express default is a private LAN address).
6. **Schema prerequisite**: every one of the Worker's 219 SQL statements was parsed and planned by a real Postgres 17 built from the Express boot DDL (`npm run migration:validate-sql`): none fails because of the port; failures are schema gaps Express shares (`docs/migration/proposed-schema-fixes.sql`; five additive columns are now applied by guarded boot migrations, the rest needs your decision). The Worker never creates tables (ADR 6.5). Tables created only by Render's boot code (see `docs/migration/required-schema.md`) must exist in the target Neon DB before the corresponding prefix is flipped. `npm run migration:check-schema` checks this (read-only) once you point it at a database.
7. **Checklist item 16** — explicit decision to ship the unguarded mock `verify-payment` (ported as-is; pinned by a test named `KNOWN UNGUARDED MOCK VERIFIER`).
8. Cutover itself (T5.1–T5.10), observation windows, rollback rehearsal — see the runbook's playbook. Nothing in `frontend/vercel.json` has been touched.

**Deliberate parity decisions** (behavior preserved, listed so they aren't mistaken for bugs in the port; each has a fix for the post-cutover PR): existing Express bugs recorded per slice in `docs/migration/wave/*.md` (see the per-slice notes; for example `RemotiveSource` always returns `[]` on Render because `node-fetch` is not installed, and the Worker matches; the open security items are in [migration/security-review-2026-09-19.md](migration/security-review-2026-09-19.md)). Platform-forced differences (case-sensitive routing, no ETag / JSON `charset`, malformed `%`-escape in path params passes through instead of Express's 400, per-isolate `aiCache` and in-memory admin demo data) are listed in the slice notes.

**Behavior differences you should know about:** (a) PDFs now parse where Render can fail — pdf.js v1.10.100 intermittently throws `bad XRef entry` when handed a Node `Buffer` (data-dependent); the Worker passes a `Uint8Array`. So `/api/resume/v2/*` and `/api/ats/v2/parse` succeed on some files Render rejects, and `/api/resume/upload` scores real text where Render scored raw bytes. (b) A disallowed CORS origin returns a masked 500 (Express bug preserved). (c) `requirePlan` fails **closed** on a non-numeric tier where Express failed open (ADR 6.3 requires it).

## Alternative worth considering

If the document-generation dependencies (step 5) turn out to be broadly incompatible, Cloudflare also offers container-based deployment products for full Node.js workloads, which would let you keep Express/`pg`/`bcrypt`/`multer` entirely as-is and get Cloudflare's edge network without a runtime rewrite. Worth a cost/complexity comparison against the full Workers port before committing to this plan — ask if you want that comparison done before starting.
